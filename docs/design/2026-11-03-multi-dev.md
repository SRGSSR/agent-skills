# Several developers and long-lived projects

- Date: 2026-11-03
- Status: implemented (skills v0.3.0)
- Scope: `skills/work-journal/SKILL.md` (handoff per branch, journal header, `.gitattributes`, end of a branch's task, upgrade from 0.2), `skills/project-phase/SKILL.md` (`.gitattributes` for `debt.md`), README "Teams and long-lived projects", eval 11

## Why

Up to 0.2 the handoff was one file, `.ai/handoff.md`, rewritten by every session. With several people on different branches the last writer silently erases the others' state, and an agent can resume someone else's plan. That is the serious problem. The journal and the debt list only produce textual merge conflicts: two branches append to the same file, so git always reports a conflict, which is trivial to resolve but annoying.

On projects that live for years (a website that keeps evolving) the journal grows without limit. Resuming never read the whole journal, so the reading cost was already bounded; the real loss is that decisions and dead ends get buried and nobody finds them again.

## Decisions

- **One handoff per branch, always**: `.ai/handoff/<branch>.md`, `/` in the branch name replaced by `-`. It maps one to one to git flow features. Agents never touch other branches' handoffs.
- **No index file** of active streams (the 0.2 "parallel work" section had one): a file everyone updates is itself a conflict point. `ls .ai/handoff/` is the index.
- **Delete the branch handoff when its task is done**, instead of the 0.2 idle state. Done means nothing is left for an agent; review and merge by people don't count. The file stays in git history.
- **Before deleting, move what must last** (decisions, dead ends) to where people look: a code comment next to the code, design docs or ADRs, or a custom rule in `.ai/phase.md`. This is the answer to the buried-journal problem: the journal stays a log, durable knowledge lives elsewhere.
- **Journal and debt stay shared**, with `merge=union` in `.gitattributes` (each skill adds the line for its own file). Union keeps both sides of an append-only file. Order can be off, but entries have a time.
- **Branch in the journal header** (`## HH:MM · tool/model · branch · topic`), so entries of different streams in one day's file stay apart. The branch instead of the person's name: the author is already in `git log`, and no personal data goes into the files.
- **`linguist-generated=true` only on the journal**, so its diffs are collapsed in GitHub pull requests. Handoff, phase and debt changes stay visible in review.
- **Find the newest journal file with `ls .ai/journal | tail -n 1`**: listing the folder of a project with years of daily files would fill the context.
- **Same branch, two people**: pull before rewriting the handoff, merge instead of overwriting, ask if the two disagree. No file layout solves this case fully.
- **Merges done by people are logged at the next resume**, in both directions: the agent is not there when the user merges, git already records the fact, so the next session notes it in one line, in the next commit it makes anyway, instead of a git hook (which would leave an uncommitted change on `develop` after each merge and only work where installed). A dedicated commit was discarded: on `develop` every commit needs the user's confirmation, so each closed feature would cost an extra question.
- **A merge into the branch (typically `develop` → feature) can make the handoff stale**: a step already done, a file moved, a dead end no longer one, a phase change. The textual merge is no problem (union for the journal, other handoffs untouched); the content is. At resume the agent finds merges with `git log --merges`, compares `git diff --stat <merge>^1 <merge>` with the files the handoff relies on, updates the handoff and raises plan changes. Reading the whole merge diff at every resume was discarded as too expensive: the file list is enough to know where to look.
- **Upgrade from 0.2**: a different work-journal block in `AGENTS.md` is replaced; an existing `.ai/handoff.md` is read as the handoff of its branch and moved on the next write (deleted if it is only an idle state).

## Evals

- Eval 11 (`parallel-handoff`) has a colleague's open handoff for another branch in the repo; it checks that the agent resumes its own branch, leaves the other alone, names the branch in journal headers, and keeps the zero-duration decision in a comment if it deletes its handoff. The fixture has `state-in-baseline`: the baseline reads the same `AGENTS.md` block, so the eval measures what the skill adds over the block.
- `resume-from-handoff` (evals 4 and 10) keeps the 0.2 layout on purpose, to cover the upgrade.
- Eval 12 (`merge-from-develop`): after the handoff, `develop` was merged into the feature and brought the test data file that step 2 of the handoff says to create. The agent must reuse it and record the merge. To express this, `evals/fixtures/build.sh` gained `@checkout`, `@merge` and `@state` (where the skill state is committed) in `history.txt`, and an `extra/` overlay so the fixture can reuse another fixture's `base/` through a symlink.
- First runs showed two gaps, both fixed in the skill text. (1) The upgrade lived only under Setup and the agent skipped it as "an unrequested change", asking instead: the skill now says the upgrade is part of the protocol and points to it from Resuming. (2) The agent deleted its handoff saying the decisions were "in the code and the journal": the skill now says the journal doesn't count and code that implements a decision doesn't say why. The example there is deliberately not the one in the eval.

## Alternatives discarded

- *Everything per branch* (`.ai/<branch>/{journal,debt.md,handoff.md}`): debt belongs to the code, not the branch, and survives the merge; it would end up in folders named after closed branches, and fixing it from another branch would mean editing someone else's folder. The journal is consulted later from other branches; split per branch, dead ends recorded on one branch are invisible to the next, and the folders either pile up or get deleted with the history. With `merge=union` the gain on conflicts is small.
- *One journal file per author*: no conflicts, but a fragmented history and people's names in the files.
- *Journal on a separate branch or in `git notes`*: invisible to agents of other tools; goes against plain Markdown in the repo.
- *Journal not committed, handoffs only*: still possible for privacy, but loses the shared record of decisions and dead ends.
- *Periodic generated summaries of old journals*: cost tokens every time, create a second version of the truth that can drift, and don't solve "nobody looks there".
- *Year subfolders for the journal*: only help humans browsing by hand, and would change the layout of existing repos; `tail -n 1` makes them unnecessary for agents.
- *Automatic deletion of old journals*: the skill never deletes history on its own; a team can prune by hand.

## Open points

- Whether merge buttons of GitHub and GitLab honor `merge=union` was not verified. Local merges (`git flow feature finish`) do.
