# Design notes

Why the skills work the way they do, and what was discarded. This repo keeps its design decisions here, one section per topic, and in code comments (its own `work-journal` block names this file). For what the skills do, see the [README](../README.md) and each plugin's README and guides.

## On / off

- `off` leaves a one-line marker (`<!-- project-phase:off -->`) instead of just deleting the block: the skills trigger on common phrases and `work-journal` sets itself up on the first journal entry, so a deleted block would come back. Discarded: the off state in `.ai/` (an extra read on every trigger, and `work-journal` has no state file), commenting the block out (it contains HTML comments, which don't nest, and would still cost context), a global switch (uninstalling is that).
- While off, an explicit request is still served once, with a one-line reminder: refusing would be unhelpful, silently turning the skill back on would defeat `off`. `.ai/` is never touched by on/off.
- `project-phase on` rebuilds the block from `.ai/phase.md` like setup does, so `off` first moves hand-added bullets to `## Custom rules`.
- The skills are written in English only, and triggers work in Italian, French and German without examples. Replies follow the user's language (the English skill text pulled replies into English before this was stated); files keep the language they already use. Forcing files to English was discarded: a team writing its journal in German should not get mixed-language files.

## Several people, long-lived projects

- One handoff per branch, no index file of active work: a file everyone updates is itself a conflict point, and the branches that hold a handoff are the index. Deleted when the branch's task is done instead of left in an idle state.
- Journal and debt stay shared, with `merge=union`. Discarded: everything per branch, `.ai/<branch>/` (debt belongs to the code and survives the merge; dead ends recorded on one branch would be invisible to the next); one journal per author (fragmented history, names in files); the journal on a separate branch or in `git notes` (invisible to other tools); periodic summaries of old journals (cost tokens and become a second truth that drifts); year subfolders (`ls .ai/journal | tail -n 1` makes them unnecessary); automatic deletion of old journals.
- The journal header names the branch, not the person: `git log` has the author, and no personal data goes into the files. `linguist-generated` only on the journal, so handoff, phase and debt changes stay visible in pull request reviews.
- Merges done by people are logged at the next resume, in the next commit the agent makes anyway. Discarded: a post-merge git hook (leaves an uncommitted change on `develop`, works only where installed) and a dedicated commit (an extra commit, and on many teams an extra confirmation, for every merge).
- A merge into the branch (`develop` → feature) can make the handoff stale. At resume the agent compares `git diff --stat` of the merge with the files the handoff relies on; reading the whole merge diff every time was discarded as too expensive.
- Not verified: whether GitHub and GitLab merge buttons honor `merge=union`. Local merges do.

## Project phases

- The contract wins over generic coding-style instructions (global rules, style plugins) where they conflict, because it is the team's choice for one project; explicit user requests still win for a task. Without this line, a global "always fix the root cause" or "no scaffolding" rule and the phase contract were resolved differently each time. Maintenance makes the most common conflict explicit: fix at the root only if no other caller changes behavior.
- The plan of a transition (prototype → stabilize takes weeks) lives in `.ai/debt.md` as open items with a priority (`must`, `soon`, `later`), not only in the conversation. Discarded: the handoff (bound to one branch) and a plan section in `phase.md` (a second list next to the debt).
- Fixed debt items are deleted, not marked: the file stays short, and with `merge=union` two branches changing the same line's status would leave both versions. Accepted items stay, because they record a decision.
- Asking for the phase in repos without one is opt-in (`project-phase: ask` in the global instructions): otherwise every repo without a block would load the skill and get a question, also for people who installed the skill for one project. An unanswered question is not recorded (no "asked, no answer" state to maintain); the agent asks again at most once per session and meanwhile states the phase it assumes. A confirmed phase is a history line, so the next session doesn't ask again for the same signal.
- Explore findings and production observations the user wants to keep go to design decisions, tasks or the debt list: the final message alone gets lost.

## Design decisions and tasks

- In `docs/` or a tracker, not in `.ai/`: they are written for people and outlive branches, while `.ai/` is the agents' working state. Both are optional, because some teams want no extra folders.
- One file per task with no status field: separate branches touch separate files, and the merge closes the task by deleting its file. Discarded: a single `ROADMAP.md` (every branch edits the same lines; `merge=union` would duplicate edited lines), a status field (git and the branch already say it), the agent assigning tasks on its own.
- Follow-ups and open questions become tasks at the end of a branch, because in the journal nobody finds them again.

## Trackers and `/backlog`

- Trackers are reached through their CLIs (`glab`, `gh`, `acli`), with a connector only as fallback: a CLI works with any agent, a connector only in tools that support it. Every write to a tracker needs the user's confirmation, even when typed as a command, because others are notified and git can't undo it; task files don't, because git can.
- When a CLI is not logged in, the agent offers the login command and stops. It never asks for a token in the chat, and never falls back to a task folder or to guessed issues.
- Jira is detected from issue keys repeated in branch names and commit subjects, because the git remote says nothing about it; the code can stay on GitHub or GitLab. Jira has no `Closes #42`: a work item is moved to Done after the merge, with the status names of the project's workflow (asked when unclear).
- Sprints are the team's planning: new work items go to the backlog, and the agent never moves a work item into or out of a sprint, deletes or archives one. The listing runs two searches, current sprint and the rest, because JQL can't sort by "in an open sprint".
- Subcommands are fixed words: `/backlog filter <condition>` rather than `/backlog <condition>`, which would clash with a condition like "close". Names chosen to avoid clashes: `/backlog` (not `/task`, close to built-in commands) and `setup` (not `init`, which Claude Code uses; "setup" is also the skills' own term).
- `.ai/team.md` is a Markdown table the agent reads, not a script: the skills stay plain Markdown for any agent, a few dozen rows need no program, and two people with the same nickname need a question anyway. It holds personal data, so it exists only when someone asks for it: never proposed at setup or when a name is missing, and the agent warns before collecting anything. Whoever asks chooses whether it is committed (one shared file, with names everyone with access already sees in `git log` and the tracker) or ignored by git; in a public repo the agent recommends ignoring it, because linking accounts, nicknames and roles would put them online. The columns are padded so the table reads in plain text. It is filled from git authors and tracker members, matching people by name and asking about uncertain matches; Jira gets the account ID, never an email. Roles only drive suggestions: the agent never assigns on its own.
- `/start` and `/finish` bracket one branch, not one session: a branch spans many sessions, paused and resumed through its handoff. `/finish` requires the mode (`merge`, `merge-request` or `mr`, `pull-request` or `pr`) because how work is integrated is the user's choice; without git flow, `merge` goes back into the branch recorded as `Base:` in the handoff, since git doesn't remember where a branch started. Names: `/finish` rather than `/close`, which `/backlog close` already uses for tasks, and the words of git flow (`feature start`, `feature finish`). With `mr` and `pr`, the handoff deletion is committed in the request itself, so merging it in the web UI completes the work. When a branch's task looks done, the agent suggests `/finish` and waits instead of closing it on its own, so the checks run in one place and the user picks how to integrate.
- `/start` checks that the base is not behind `origin` before branching, since a feature started from a stale base brings conflicts at `/finish`. It asks rather than pulling: updating the base is the user's choice, and only by fast-forward, so the agent never merges into it on its own. It checks only for commits missing locally (local commits not yet pushed are the user's business), and a failed fetch doesn't block the start, it is only reported. Resuming a paused branch runs the checks of `/finish` instead (branch and base against `origin`, conflicts with the base), because a branch paused for days is where the base moves away: conflicts found while resuming are cheaper than at the end.
- `/finish` checks that the branch and its base are not behind `origin`, and that the branch merges into the base without conflicts (`git merge-tree`, which touches nothing), against both the local base and `origin/<base>`: a merge request goes into the remote one, a local merge into the local one. Being behind is the user's call (update first or continue); conflicts are not, they are resolved before the branch is closed, so they never surface halfway through `git flow feature finish` or in the review. Conflicts are resolved by merging the base into the branch, never by rebasing, which would rewrite pushed history; the agent resolves them after the user's yes, asking where the sides contradict, then runs the tests again.
- `/request` covers merge and pull requests with fewer commands than `/backlog`: no `new`, because a request is born from `/finish mr` or `pr`, which runs the checks, and two places to create one would drift apart; no `close`, which is rare and one click on the host; no `filter`, because the listing is short and a name after `/request` is enough. `show` is implicit (`/request <id>`), the one thing an ID alone can mean. The listing goes by what only the user can unblock: first the approved requests assigned to them (one command from done), then those waiting for their review (they block someone else), then the rest of theirs, which wait for others. A table per group, because the useful person column differs (who approved, the author of what you review, the reviewers of what you wrote). GitLab's listing doesn't say whether a request is approved, so the approvals are read one by one, only for the requests assigned to the user.
- `/request test` runs the `How to test` part that `/finish` writes, so the description is both the reviewer's guide and the agent's script. It runs in a detached worktree fetched from the request's head ref (`pull/<n>/head`, `merge-requests/<n>/head`), which works for forks too and never touches the user's branch. The steps were written by the author's agent, so they are checked against the issues: a specification with no step gets one, marked as added. What can't be run is reported as not run rather than guessed, and nothing is fixed, committed or posted without a yes: a test that repairs what it tests proves nothing. A request from a fork is asked about first, since testing executes its code. Discarded: wrapping a code review tool (Claude Code's `/code-review` exists only there, and it reads the diff, while this runs the plan).
- `/request review` is the reviewer's path in one command: show, test, then a read of the diff limited to what tests can't show and an agent can check against something written (the issue's specifications, the description, the docs, the project's rules). Hunting bugs line by line is left to a code review tool, which the review suggests at the end and never runs unasked: those tools differ per agent and can cost money. An empty list of findings is a valid result, so the agent has no reason to invent one.
- The verdict has two commands, `/request approve` and `/request changes`, and only the user gives them: an approval says that a person checked the work, so the agent that ran the review never runs one on its own. Its advice is one-sided: it recommends asking for changes when a step failed or a finding blocks, because those are facts the reviewer can check and the reasons are ready to send; it never recommends approving, because it did not read the code for bugs and could not run every step, and "I recommend approving" would be read as "it is fine". With nothing blocking it lists what is still missing before an approval. Before approving it asks about every step it could not run or that failed, as a question of its own that a bare "yes" or a repeated command doesn't answer: those are exactly the steps an agent's "all passed" hides. The approval is tied to the commit that was tested (`--sha` on GitLab, a re-read of the head on GitHub). The second command is `changes`, not `reject`: on both hosts the reviewer's no is "request changes" and leaves the request open, while "reject" suggests closing it; the word is still understood. `glab` has no request-changes command, so on GitLab it is a comment plus the revoke of an approval, and the skill says that the formal state is set on the host. Closing stays on the host.
- `/request merge` came last and with the most checks, because it is the one step that can't be undone: approved by someone else, green, no conflicts, no open comments, the approved commit (`--sha`, `--match-head-commit`), and never a way around what the host refuses. The hosts decide who may merge by permissions, not by the assignee field, so the skill refuses nobody; but the merge belongs to the assignee (or the author), and anyone else, the reviewer who just approved included, is asked first in a question separate from the confirmation: one "yes" must not cover both "it is mine to merge" and "merge it now". On GitLab `--auto-merge=false`, since `glab` would otherwise leave a merge pending on the pipeline. It doesn't replace `/finish merge`, which merges locally a branch that has no request.
- `/pause` is a command of its own, next to "let's stop here": in words the agent writes the handoff from what it has, while `/pause` first looks for what is missing (decisions taken in the chat, problems, things outside the repo) and asks, which is too slow for every end of session. It leaves the tracker task as it is (a paused task is still in progress and assigned), and never stashes: a stash is invisible to another session and stays on one machine. Uncommitted work is the user's choice between a `wip:` commit, which travels, and the working tree. Why and until when goes in a `Paused:` header line of the handoff, not in a status field or an index of paused work: the branches that hold a handoff already are that list. Resuming has no command of its own (`/resume` is a Claude Code built-in): `/start` resumes a branch that exists, and `/start` alone the current one. The `AGENTS.md` block doesn't mention `/pause`, so existing repos need no block upgrade.
- The description of a merge or pull request has three fixed parts (a short introduction, the changes in detail, how to test with specifications and their issues, steps and edge cases): whoever reviews or tests was not in the conversation, and "how to verify: `npm test`" leaves them guessing what the work had to do. All three stay even for a small change, each as short as it can be, so a reviewer always finds things in the same place; what nobody ran is marked as such rather than left out. Reviewer and assignee are both asked when the instructions don't name them, as one question in the same message as the confirmation: they are different roles (the reviewer is the check by someone else, the assignee carries the request to the merge and is often the author), who takes them is the user's call, and a second stop would be noise. Discarded: asking only for the assignee, which leaves out the very check a request exists for.
- `/finish` checks the docs only for what the branch changed, not the whole documentation: an audit on every finish would cost too much and stop on old gaps. It asks for an example only where the docs already show examples for similar things, so it follows each project's own style instead of imposing one.
- `/finish` removes the worktrees an agent tool left for its subagents (Claude Code: `.claude/worktrees/agent-<id>`, branch `worktree-agent-<id>`), since nobody else cleans them up after the branch. Only those that hold nothing left: no uncommitted changes and no commit whose changes are missing from the branch (`git cherry`, so cherry-picked work counts as in); for the others it asks, since it may be lost work. Their branches go with `-D`, because `-d` doesn't see cherry-picks; the rule "never `-D`" stays for work branches. The user's own worktrees are never touched.
- Listings are tables (task, title, assignee, priority, status): columns line up and are easier to scan than lines with separators. Others' tasks stay a count under the table. A listing of only the user's own tasks drops the assignee column, which would repeat one name on every row; a mixed listing keeps it, because it is what tells yours from the unassigned.
- A task assigned to someone else carries a body that explains the work (what, where, what is known, whom to ask): the assignee was not in the conversation, and a terse body hands them a guess. A task for the user stays terse, since they have the context.
- Postponed tasks show the date they can resume, looked up only for tasks marked postponed (a label, status, milestone or `Postponed:` line), so a listing doesn't read every body. A due date is a deadline, not a resume date, so it is never used for it. A postponed task is not suggested before its date, or ever without one; the agent never removes the mark itself.
- A listing fetches at most 100 tasks (the CLIs default to 30, which silently cut longer backlogs) and says when there may be more.

## Soft mode

- For people who work with care but avoid task trackers: fewer tasks, reminders in the handoff, gentle prompts. Only text in the existing skills, no new skill or file: the handoff is already read at every resume and committed.
- Per person, not per project: the line `work-journal: soft` in the person's global instructions, like `project-phase: ask`. The `AGENTS.md` block does not change (no block upgrade in existing repos, and a project file can't hold a personal setting); the skill's description names the line, which is what loads the skill. Each tool has its own global file, so it is on per tool.
- Reminders go in the committed handoff, not in a personal file outside git: they travel with the branch and reach whoever takes it over. Each line carries the handle of who noted it, so the agent reminds only that person; anyone rewriting the handoff keeps all of them, in soft mode or not.
- "Can't be done soon" means "not before this branch finishes": a reminder ends with its handoff, so that is the one threshold an agent can decide without guessing. The agent says which case applies and the person decides.
- No reminders on the development or default branch: no `/finish` ever closes that handoff, so they would pile up. There the agent offers a task or `/start`. Discarded: cleaning up old ones at resume, moving them into the next feature's handoff.
- At `/finish` every reminder is closed one by one (done, dropped, task), in soft mode or not: nothing is lost with the deleted handoff, and nothing becomes a task without the person wanting it.
- Assigned tasks are all those assigned to the person, not only those created by others: telling them apart costs a query per tracker, and task files have no author. They are read at every session start on a branch without a handoff, and after `/finish`; a tracker that is not logged in is skipped silently, since a login prompt nobody asked for is the opposite of gentle.

- `soft once` holds only in the conversation and writes nothing: a way to try the mode, or to use it on one task, without touching the global file. A long session that gets compacted may lose it; accepted, since a marker file would need cleaning up after sessions that end without notice.

## Session start hooks

- Claude Code can't speak first: without a hook, a session in a branch with a handoff starts with an empty prompt, and resuming depends on the agent noticing the block. Each plugin has a `SessionStart` hook (`startup|clear`: after `/clear` the context is as empty as at startup; `resume` and `compact` keep it). Modeled on the welcome hook of an internal CLI. Claude Code only; other tools keep relying on the `AGENTS.md` block, so the hook adds nothing they need.
- `work-journal`: a `systemMessage` for the user and `additionalContext` for Claude, only when there is something to resume (a handoff on the current branch, or other local branches with one). Silent otherwise, so it costs nothing in most sessions. The context points to the skill's Resuming instead of restating it, so the two can't drift; it names files, never copies the handoff.
- `project-phase`: one line with the phase, for the user only (user's choice); Claude already has the block. Each plugin has its own hook instead of one hook printing both: the plugins don't need each other.
- POSIX `sh` and `git` only: the plugins have no runtime, Claude Code may be installed without Node, and on Windows it runs hooks in Git Bash. JSON is escaped by hand (backslash and `"`; git refnames can't hold control characters). A hook never fails the session: every error path exits 0 with no output.
- A handoff is committed on its own branch, so `ls .ai/handoff/` on `develop` showed none of the paused work; the hook, the Resuming step and `/start` now look in the local branches (`git cat-file -e <branch>:<handoff>`, `git ls-tree`). Remote branches are left out of the hook: listing them needs a fetch to be current and doubles every local branch.
- `scripts/test-hooks.sh`, run by CI, builds throwaway repos; every git command names its repo with `-C`, so a failed `mktemp` can't touch the checkout (it happened while drafting).

## Token cost and scripts

Measured on 2026-11-25 with evals run by Sonnet subagents: a bare subagent costs about 50k tokens, a skill command 10 to 24k on top, and the skill text was the largest single part of that.

- **A short `SKILL.md`, the rest in `references/`**, read only by the commands that need it: `backlog` (writing tasks, `.ai/team.md`), `request` (test and review, approve, changes and merge), `work-journal` (setup and on/off, soft mode), `finish` (the merge or pull request). A listing, `/backlog help` and a Jira listing went down by about 4k tokens each (a quarter of the skill's share); commands that read a reference cost about the same as before. The evals graded the same before and after. Kept in `SKILL.md`: what every load needs, like the block template (resuming compares it), what off means and when soft mode is on. `scripts/check-skills.mjs` checks the anchors of links between files, since moving sections breaks them silently.
- **Scripts only for deterministic work that needs no judgment**: the git checks of `/finish` and of `/start` when resuming are one command, `finish/scripts/git-checks.sh` (POSIX sh and git, like the hooks), which prints one line per check. Its gain is fewer steps and the same checks every time, not tokens: about 1 to 3k less and 5 to 6 tool calls instead of 5 to 10, with the same grades. Its `git fetch` doesn't prompt and gives up on ssh after 10 seconds. The skill keeps the list of checks, so an agent without `sh` can still run them by hand (`/finish` and `/start` both say so; evals 58 and 59 check it). On Windows, Git for Windows puts only `<install>/cmd` on PATH by default, where there is `git.exe` but no `sh.exe`: setup looks in `<install>/bin`, found from `git --exec-path`, and suggests adding that folder, not `usr/bin`, whose Unix tools shadow Windows ones. Discarded: a PowerShell or Node twin of the script, two copies of the same checks to keep in sync for a rare case.
- **Listings ask the CLI for the fields they show** (`--jq` in `gh` and `glab`, a header line and one TSV line per item) instead of reading JSON. Measured on public projects: 100 open GitLab issues in `glab -O json` take about 140k tokens, because every description comes along; the filtered listing takes about 5k. On GitHub, 83 issues take about 10k as `--json` and 2.3k filtered. Discarded: a listing script per tracker, since the CLIs do the filtering themselves and the judgment (postponed tasks, who is who, what to suggest) stays with the agent anyway. Jira still reads JSON: `acli --csv` looks like the same gain but its output is untested.
- **No script to align `.ai/team.md`**: asked to add a row that widened two columns, Sonnet kept the table aligned 3 times out of 3, so a script would add upkeep and no gain.

## Layout, names and manifests

- One folder per plugin (`plugins/<plugin>/skills/<skill>/`) instead of one `skills/` at the root shared by both plugins: the Anthropic plugin directory takes one plugin folder per submission and refused the shared root, and each installed plugin now carries only its own folder. `npx skills add` finds skills nested this way. Links between skills stay inside the work-journal plugin, so the split broke none. Discarded: one plugin with all five skills (forces both on everyone and changes the install ids), symbolic links from a root `skills/` (the directory doesn't count linked skill folders, and they break on some Windows checkouts).
- A plugin's version lives only in its `.claude-plugin/plugin.json`: `claude plugin validate --strict` wants it there, and a second copy in `marketplace.json` would drift. The marketplace entry keeps name, source and description, which people see while browsing.
- Skill descriptions are double-quoted in the frontmatter: strict YAML parsers skip a plain value that contains `: ` (`npx skills`, with skills 1.8.1, installed three of the five skills). Claude Code tolerates it, so the failure was invisible there. CI therefore parses each frontmatter with `yaml`, the parser `npx skills` uses, as well as running `claude plugin validate`: each consumer accepts something the other rejects.
- Repository `SRGSSR/agent-skills`, marketplace `srgssr`: renamed before the public launch, while few people had installed it. The old `srgssr-` prefix repeated the owner, and "agent skills" is what people search for; the repository can also host further skills from SRG SSR. So few people had installed it that the README carries no migration notes: removing the old marketplace uninstalls its plugins, then they add the new one.

## README and public texts

- Section headings stay without emoji: guides link to anchors such as `README.md#install` and a plugin README's `#disable-or-uninstall`, and an emoji changes the anchor. Emoji go in tables and lists.
- Public texts (README, posts, list entries) mention SRG SSR briefly and at the end, as where the project started ("Started by people at SRG SSR"), not as the voice of the project: the skills are not used across the company, and the collection should read as open to anyone. SRG SSR stays in the collection's name and as licensor.
- Eval numbers are quoted with their date, the skill versions and the number of cases, and say where the model already did well without the skills: a bare "126/126" reads as more than it measured.
- Plugin icons and the social preview follow the SRG SSR family's look, read from the RSI, SRF and RTS stylesheets: flat, red `#af001e` (RSI's theme color), text `#171717`, light grey `#f5f5f5`. Sources in `docs/assets/`. SRG SSR Type, the family's typeface, is proprietary, so Inter stands in.
- The root README is a catalog with a showcase: what the collection is, install, then per plugin what changes for the user (one request, three phases; a session handed from one tool to another) and a link to its full docs, then the evidence. Each plugin's README holds its full docs (phases or commands, how it works, cost, disabling), so it stands alone in the plugin directory. Reference material is folded in `<details>`, and the reasoning lives here.
- Guides live with their plugin (`plugins/<plugin>/docs/`), not in a shared `docs/`: the plugins don't need each other, and a later plugin brings its own. Where two plugins work together, each guide says how in a short "With …" section. Discarded: one set of guides covering both plugins (the previous layout, which mixed their steps in every guide).
