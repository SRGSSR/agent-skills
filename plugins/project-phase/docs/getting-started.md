# Getting started with project-phase

How to set the phase in a brand-new repo or in one with history, and what changes while you work. Install the plugin first ([Install](../../../README.md#install)).

## Defaults for every project (optional)

If you want the same defaults in every project, add them to your global agent instructions (for example `~/.claude/CLAUDE.md`):

```
project-phase set: simple
project-phase: ask
```

- `project-phase set: simple` uses the set prototype → production → maintenance without asking. Without it, setup proposes `standard` (with stabilize between prototype and production).
- `project-phase: ask` makes the agent ask for the phase before the first code change in any repo that has none. Without it, the phase is set up only when you ask.

## A new repo

For a repo that is empty or a few days old, where you want to try an idea quickly. Ask the agent:

> Set up the project phase for this repo.

Or `/project-phase setup`. The agent looks at a few cheap signals (file listing, README, git log, CI, tests, deploy files), proposes a phase and a set with two or three lines of reasoning, and waits for you to confirm. For a new repo the proposal is usually `prototype`. Choose:

- **`explore`** if the code is disposable and the output is an answer ("can we parse these feeds fast enough?"). It is in the `full` set or in a `custom` one.
- **`prototype`** if you are building a first working version to validate the idea.
- **`production`** if the repo is new but the product is not: a rewrite of a live service has real users from day one.

After you confirm, the agent writes:

| File | What |
|---|---|
| `AGENTS.md` | The contract block, about 15 lines, loaded on every task |
| `CLAUDE.md` | `@AGENTS.md` near the top, only if `CLAUDE.md` exists (Claude Code reads `AGENTS.md` only without a `CLAUDE.md`) |
| `.ai/phase.md` | Set, current phase, area overrides, custom rules, history |
| `.gitattributes` | `.ai/debt.md merge=union`, so two branches adding debt never conflict |

`.ai/phase.md` looks like this:

```markdown
# Project phase

Phase set: standard (prototype → stabilize → production → maintenance)
Current: prototype (since 2026-11-04)

## Area overrides

## Custom rules

## History
- 2026-11-04: set to prototype (setup). New repo, validating the idea with two pilot users.
```

`.ai/debt.md` is created only when the first shortcut is logged.

## A repo with history

For a repo that may be live, with its own `CLAUDE.md`, ADRs or tracker. The skill fits around what is there instead of replacing it.

> Set up the project phase for this repo.

Or `/project-phase setup`. The agent reads cheap signals only, never the source tree: file listing, README, the last 20 commits, commit count and age, CI, tests, deploy files, version and tags, CHANGELOG. Typical readings:

| Signals | Proposed phase |
|---|---|
| Weeks old, one or two contributors, version 0.x, no production deploy | `prototype` |
| Prototype signals plus recent commits adding tests, CI or config; a launch is coming | `stabilize` |
| Deploy config, CI running tests, release tags or version ≥ 1.0, CHANGELOG, migrations, monitoring | `production` |
| Production signals, but recent history is mostly fixes and dependency bumps, patch releases only | `maintenance` |
| Deprecation notice, "replaced by" in the README, shutdown timeline | `sunset` |

Signals only suggest: the phase is what the team wants to optimize now, not the repo's age. An old repo can be back in prototype for a new direction. When signals conflict, the agent says which ones and asks.

### Parts of the repo in another phase

If parts clearly differ, the agent proposes area overrides, for example:

```markdown
Area overrides (apply the phase of the files you change; strictest wins if a change spans areas):
- `legacy/billing/` → maintenance: smallest diff, touch nothing else, regression test.
- `experiments/` → explore: disposable code, the output is the learning.
```

### Project-specific rules

The generic contract can't know your project. From what it read, the agent proposes up to three rules where a mistake would be costly, one line each, for example:

- Migrations that already ran are never edited; add a new one.
- Old mobile app versions keep calling the API: responses only grow, fields are never removed or renamed.
- `src/generated/` is generated by `npm run codegen`; never edit it by hand.

Accepted rules go under `## Custom rules` in `.ai/phase.md` and into the contract block. Keep them few: the block is loaded on every task. You can add one later in words ("add a project rule: ...").

### Existing instruction files

- An existing `AGENTS.md` keeps its content; the block goes near the top.
- An existing `CLAUDE.md` gets `@AGENTS.md` near the top, unless it already imports it. The block is never copied into both.
- Your global instructions and style plugins (a minimalism plugin, "always add tests", ...) still apply, within the phase. Where they conflict, the phase contract wins, because it is the team's choice for this project. Your explicit request still wins for the task at hand.

### Debt that already exists

`.ai/debt.md` starts empty. In production the agent records debt it finds while working, and mentions known debt when a task touches that area. To take stock in one go, ask for a debt review, or run a phase transition: the prototype → stabilize checklist also searches `TODO`, `FIXME` and your own markers, and adds the ones that matter.

### Changing the choices later

Run `/project-phase setup` again on a project already set up. The agent shows the current set, phase, overrides and rules, reads the signals again and proposes only what they suggest changing, for example a phase that no longer fits. It changes only what you confirm. The phase history and the debt list stay as they are.

## Working in each phase

**Prototype:** what changes compared to an agent without the skill:

- It builds what you ask, the simplest way that works: no extra layers, configs, test suites or CI you didn't ask for.
- It picks sensible defaults instead of asking, and states them in one line.
- No list of "improvements you should consider". It mentions only blockers: security holes if exposed, data loss, dead ends.
- Deliberate shortcuts that would hurt later get one line in `.ai/debt.md`:

  ```markdown
  - [open] 2026-11-04 · `src/auth/` · Auth stubbed: any email logs in. Fix before real users.
  ```

**Production:** the agent follows existing patterns, tests new code, adds a regression test to every bug fix, keeps APIs and data backward compatible, and records tech debt. At the end of a task it may add up to three short structural observations about the area it touched (problem, impact, effort). It doesn't implement them unasked; if you want to keep one, it becomes a task or a debt line.

**Maintenance:** the smallest diff that fixes the problem, nothing else touched, a regression test, no dependency or interface changes unless the fix needs them. Issues it notices are written down, not fixed. A bug in a shared function is fixed at the root only if no other caller changes behavior; otherwise the agent fixes the reported path and records the other callers in `.ai/debt.md`.

The phase sets defaults, not prohibitions: "add tests for the export" gets you tests. Three rules hold in every phase: no secrets in code or logs, no destructive operations without confirmation, an honest account of what is untested.

## With work-journal

`project-phase` works on its own. With [`work-journal`](../../work-journal/README.md) also installed, the handoff records the phase in its header, phase changes are logged in the journal, and in explore and prototype the journal keeps only decisions, dead ends and session ends. `.ai/debt.md` keeps tracking shortcuts in the code; when the team decides to fix one, the task links the debt item instead of copying it.
